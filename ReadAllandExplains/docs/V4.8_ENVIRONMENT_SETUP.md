# ReadAllandExplains 4.8 环境配置与验收指南

> 适用版本：`v4.8.0-preview.1`（MCP 服务 `0.6.0`，工具总数 `12`）
> 更新日期：2026-08-09
> 文档职责：让读者按顺序照做即可完成 4.8 接入、确认接入成功、复现验收测试，并在出错时按正确顺序定位根因。
> 重要前提：**4.8 MVP 的新能力全部在 MCP 侧，UE 插件仍是 `4.7.0`。** 因此不需要重新编译 C++、不需要重装 UE 插件、不需要重新导出资产，用现有 4.7 Context Pack 即可验证 4.8。

## 1. 你需要准备什么

| 项目 | 要求 |
|---|---|
| 操作系统 | Windows 64 位 |
| Python | 3.9 或更高，且可在 `PATH` 中以 `python` 调用（MCP 仅用标准库，无第三方依赖） |
| 客户端 | CodeBuddy 或 Trans / WorkBuddy |
| 已有数据 | 至少一个 `state=complete` 的 4.7 Context Pack |
| UE 编辑器 | **本轮不需要运行**。仅在测试 SyncLive 定向补拍时才需要 |

确认 Python 可用：

```powershell
python --version
```

## 2. 关键认知：谁才是真正的启动源

这是本轮踩坑最深的地方，务必先理解，否则会反复修错文件。

客户端启动 MCP 的方式可能有多种，实际生效的只有一个。**优先级从高到低：**

| 优先级 | 位置 | 说明 |
|---|---|---|
| 1 | CodeBuddy 插件市场注册表 `%USERPROFILE%\.codebuddy\plugins\known_marketplaces.json` | 若插件以 `directory` 类型市场注册，CodeBuddy 会用它的 `source.path` 加载插件，并执行**插件自带**的 `.mcp.json`（通过 `${CODEBUDDY_PLUGIN_ROOT}` 解析路径）。这会覆盖你在工作区做的任何配置 |
| 2 | 实际运行的 Python 进程命令行 | 唯一的事实来源。它指向哪个目录，就是在跑哪个版本 |
| 3 | 环境变量 `READALL_EXPORT_ROOT` | 插件方式启动时不传 `--root`，导出目录只能靠它或自动发现 |
| 4 | 工作区 `.mcp.json` / `config/mcporter.json` | 看起来最相关，但当第 1 项存在时它们**不生效** |

一句话原则：

> 先确认进程从哪里启动，再决定改哪个配置。不要从看起来最相关的配置文件开始改。

## 3. 配置步骤（CodeBuddy）

### 3.1 备份现有配置

改动前先留回滚副本：

```powershell
$stamp = Get-Date -Format "yyyyMMdd-HHmmss"
$reg = "$env:USERPROFILE\.codebuddy\plugins\known_marketplaces.json"
Copy-Item $reg "$reg.pre-v48-$stamp.bak"
```

### 3.2 查看当前注册表指向哪个目录

```powershell
Get-Content "$env:USERPROFILE\.codebuddy\plugins\known_marketplaces.json" -Raw
```

找到 `readallandexplains-marketplace` 这一项，确认它的 `source.path` 与 `installLocation`。如果它仍指向旧版本目录（例如带 `4.1.0_dev`、`4.7` 字样的路径），就是它导致你看不到新接口。

### 3.3 切换到 4.8 插件目录

把该项的 `source.path` 与 `installLocation` 同时改为 4.8 插件根目录，即包含 `ReadAllandExplains.uplugin` 的那一层：

```text
<你的4.8目录>\ReadAllandExplains_4.8.0_mvp\ReadAllandExplains
```

注意 JSON 中 Windows 路径需要转义反斜杠，例如 `C:\\Users\\you\\...`。两个字段必须一致，只改一个会出现加载路径与安装路径不匹配。

### 3.4 设置导出目录

插件方式启动不会传 `--root`，因此显式指定导出根目录最稳妥：

```powershell
setx READALL_EXPORT_ROOT "D:\YourProject\Saved\ReadAllandExplainsExports"
```

`setx` 写入用户级环境变量，**需要重启客户端主程序才会被子进程继承**。回滚只需删除该变量。

若只想临时生效（当前 PowerShell 会话内启动客户端）：

```powershell
$env:READALL_EXPORT_ROOT = "D:/YourProject/Saved/ReadAllandExplainsExports"
```

MCP 查找导出目录的顺序是：`--root` 参数 → `READALL_EXPORT_ROOT` → 工作区或父目录中的 UE 项目 → 当前目录的 `Saved/ReadAllandExplainsExports`。

### 3.5 结束旧进程

旧的 MCP 子进程会继续占用旧代码。先确认再结束：

```powershell
Get-CimInstance Win32_Process -Filter "Name like '%python%'" |
  Where-Object { $_.CommandLine -like "*readallandexplains*" } |
  Select-Object ProcessId, CommandLine
```

确认命令行确实指向旧目录后再结束对应进程。

### 3.6 完全重启客户端

不要只用 `Reload Window`。因为第 3.4 步的环境变量必须由重启后的主进程继承。

**完全退出客户端主程序，再重新启动。** 启动后执行：

```text
/reload-plugins
```

## 4. 配置步骤（Trans / WorkBuddy）

Trans 侧同样只需 MCP 指向 4.8，UE 插件保持 `4.7.0` 不变。要点相同：

1. 确认 Trans 实际使用的 MCP 启动配置指向 4.8 目录。
2. 确认 `READALL_EXPORT_ROOT` 或自动发现能找到导出目录。
3. 结束旧 MCP 进程。
4. 完全重启客户端，并新建会话。

**必须新建会话。** 已有会话可能沿用旧的工具清单缓存。

## 6. 复现验收测试

预检通过后，用以下三轮测试验证功能。把你的英雄资产名和 Pack ID 替换进去即可。

三轮测试通用的硬约束（写进提问里，防止模型复述历史答案）：

- 数据必须来自本轮实际 MCP 返回，禁止引用历史结果、已知 ID 或预期值。
- 必须核对每次调用的 `pack_id`、`state`、`fingerprint`，不一致立即停止。
- 必须报告 `evidence`、`warnings`、`missing_fields`、`error`。
- 必须报告 `page.truncated`、`data.budget.truncated`、`truncation_reasons`、`boundary`；字段未返回时明确写“未返回”。
- 禁止读取完整 Graph 与完整 Readable。
- 禁止调用 `get_asset_detail`、`get_asset_summary`、`search_export_text`、`request_targeted_snapshot`。
- 结尾必须列出本轮实际调用顺序。

### 6.1 测试一：Outline 与稳定章节

按 `search_assets` → `get_asset_outline` → `get_readable_sections` → `get_readable_section` 顺序执行，读取两个小章节。

通过标准：能列出全部 Graph 的完整 `graph_id`、节点数、连线数；能列出稳定 `section_id` 与字符量；按 `section_id` 精确读取的章节 `returned` 等于 `total`；**没有读取最大的那个章节**。

### 6.2 测试二：定位与最小子图

先 `locate_graph_target` 定位目标节点，再 `get_graph_subgraph` 以 `direction=upstream`、`max_hops=2`、`max_nodes=40`、`max_characters=20000` 读取上游子图。

通过标准：`resolution=ambiguous` 时列出全部候选并停下，不自行选择；唯一后返回稳定 `node_id`；子图规模远小于整图且 `budget.truncated=false`；明确声明这不是完整 Graph 闭包。

### 6.3 测试三：异常路径与预算边界

测试 A：查询一个确定不存在的目标，例如 `__RAE_NOT_FOUND_TEST_9F3A__`。
测试 B：对已定位节点设置 `max_nodes=1`，强制触发截断。

通过标准：A 返回 `resolution=not_found` 且不继续调用子图，也不把未找到解释为 Graph 或资产不存在；B 返回 `budget.truncated=true`、`truncation_reasons` 指明具体原因、`boundary` 精确给出被截断的连线，并声明不得把未返回节点视为不存在。

### 6.4 参考基线

以英雄资产 `FX_Syst_Waterfall_FXTex` 为例的实测基线，可用于比对：

```text
Outline      4 张 Graph（7/5、48/49、25/35、8/9），7 个稳定章节
子图         上游 2 跳 → 6 节点 / 5 连线 / 6,016 字符，未截断
截断态       max_nodes=1 → 1 节点 / 0 连线 / 1,954 字符
             truncation_reasons=[max_nodes]，omitted_node_count=5
```

完整数据见 `docs/V4.8_MVP_ACCEPTANCE_REPORT.md`。

## 7. 故障排查

**看不到新接口，或工具数仍是 7。**
按第 2 节优先级逐项检查，顺序不能颠倒：先看插件市场注册表指向哪里，再看实际 Python 进程命令行，最后才看工作区配置。改完必须完全重启客户端并新建会话。

**改了工作区 `.mcp.json` 却没有任何变化。**
说明它不是实际启动源。检查插件市场注册表。

**结束旧进程后它又自动出现，且仍是旧路径。**
说明客户端按注册表重新拉起了旧目录的插件。修注册表，而不是反复结束进程。

**找不到 Context Pack。**
设置 `READALL_EXPORT_ROOT` 指向 `<YourProject>\Saved\ReadAllandExplainsExports`。注意 `setx` 需要重启主程序才生效。

**MCP 起不来。**
确认 `python --version` 不低于 3.9，然后 `/reload-plugins`。本项目不需要 npm，也不需要第三方 Python 包。

**出现 `GRAPH_INDEX_DERIVED` 或 `READABLE_INDEX_DERIVED`。**
这不是错误。它表示索引由既有事实确定性派生，因为读取的是 4.7 旧 Pack。不要把派生索引说成 UE 原生字段。

**出现 `GRAPH_IDENTITY_DEGRADED` 或 `GRAPH_DATA_INVALID`。**
前者表示旧 Pack 的图身份信息不完整但仍可用于 Outline 与定位；后者表示节点 ID 重复，无法安全进行精确遍历。两者都是有意的显式降级，不是静默忽略。

**SyncLive 请求一直是 `pending`。**
需要 UE 编辑器处于运行状态、插件已加载、不在 PIE 中，且 Editor Preferences 里 SyncLive Lite 已开启。

## 8. 回滚

按修改的反序回滚即可，全部改动都有备份：

1. 用 `.bak` 副本还原 `known_marketplaces.json`。
2. 删除环境变量 `READALL_EXPORT_ROOT`（若原先不存在）。
3. 结束当前 MCP 进程。
4. 完全重启客户端并执行 `/reload-plugins`。

代码侧回滚从对应备份标签创建恢复分支，不要重写已有历史：

```powershell
git tag -l "backup/v4.8-mvp-*"
git switch -c recover/from-cp4 backup/v4.8-mvp-cp4-20260809-<sha>
```

约束不变：不使用 `reset --hard`、不强制推送、不移动正式标签、不覆盖其他 worktree 的未提交修改。

# 4.8 Environment Setup and Acceptance Guide (English)

> Applies to `v4.8.0-preview.1` (MCP server `0.6.0`, `12` tools).
> Updated 2026-08-09.
> Purpose: follow this document top to bottom to onboard 4.8, confirm onboarding, reproduce the acceptance tests, and diagnose failures in the correct order.
> Key premise: **all 4.8 MVP capability lives in the MCP layer; the UE plugin remains `4.7.0`.** No C++ rebuild, no plugin reinstall, and no re-export are required. Existing 4.7 Context Packs are sufficient.

## 1. Prerequisites

| Item | Requirement |
|---|---|
| OS | Windows 64-bit |
| Python | 3.9+ callable as `python` on `PATH` (standard library only, no third-party packages) |
| Client | CodeBuddy, or Trans / WorkBuddy |
| Data | At least one Context Pack with `state=complete` |
| UE editor | **Not required** for this round; only needed to test SyncLive targeted re-snapshot |

```powershell
python --version
```

## 2. Critical concept: which launch source actually wins

This caused the deepest confusion during onboarding. Read it before editing any file.

A client may have several ways to launch MCP, but only one takes effect. **Priority, highest first:**

| Priority | Location | Notes |
|---|---|---|
| 1 | CodeBuddy marketplace registry `%USERPROFILE%\.codebuddy\plugins\known_marketplaces.json` | If the plugin is registered as a `directory` marketplace, CodeBuddy loads it from `source.path` and runs the **plugin's own** `.mcp.json`, resolved via `${CODEBUDDY_PLUGIN_ROOT}`. This overrides anything configured in your workspace |
| 2 | The running Python process command line | The only ground truth. Whatever directory it points at is the version actually running |
| 3 | Environment variable `READALL_EXPORT_ROOT` | Plugin-based launch does not pass `--root`, so the export root relies on this or auto-discovery |
| 4 | Workspace `.mcp.json` / `config/mcporter.json` | Looks most relevant, but has **no effect** while item 1 exists |

Rule of thumb:

> Determine where the process is launched from before deciding which config to edit. Do not start with the file that looks most relevant.

## 3. Setup (CodeBuddy)

**Back up first.**

```powershell
$stamp = Get-Date -Format "yyyyMMdd-HHmmss"
$reg = "$env:USERPROFILE\.codebuddy\plugins\known_marketplaces.json"
Copy-Item $reg "$reg.pre-v48-$stamp.bak"
```

**Inspect the registry.**

```powershell
Get-Content "$env:USERPROFILE\.codebuddy\plugins\known_marketplaces.json" -Raw
```

Locate `readallandexplains-marketplace` and check `source.path` and `installLocation`. If either still points at an older directory, that is why the new tools are missing.

**Repoint to the 4.8 plugin directory.** Set both `source.path` and `installLocation` to the folder that contains `ReadAllandExplains.uplugin`:

```text
<your-4.8-root>\ReadAllandExplains_4.8.0_mvp\ReadAllandExplains
```

Escape backslashes in JSON, e.g. `C:\\Users\\you\\...`. Both fields must match; changing only one leaves load and install paths inconsistent.

**Set the export root.** Plugin-based launch does not pass `--root`, so be explicit:

```powershell
setx READALL_EXPORT_ROOT "D:\YourProject\Saved\ReadAllandExplainsExports"
```

`setx` writes a user-level variable and **requires a full client restart** before child processes inherit it. Deleting the variable rolls the change back. For a session-scoped alternative:

```powershell
$env:READALL_EXPORT_ROOT = "D:/YourProject/Saved/ReadAllandExplainsExports"
```

Discovery order is `--root` → `READALL_EXPORT_ROOT` → a UE project in the workspace or a parent directory → `Saved/ReadAllandExplainsExports` in the current directory.

**Terminate stale processes.** Verify before killing:

```powershell
Get-CimInstance Win32_Process -Filter "Name like '%python%'" |
  Where-Object { $_.CommandLine -like "*readallandexplains*" } |
  Select-Object ProcessId, CommandLine
```

**Restart fully.** Do not rely on `Reload Window`; the environment variable must be inherited by a freshly started main process. Exit the client completely, relaunch, then run `/reload-plugins`.

## 6. Reproduce the acceptance tests

Apply these constraints to every round so answers cannot be recited from history: data must come from this round's actual responses; verify `pack_id`, `state`, and `fingerprint` on each call and stop on mismatch; report `evidence`, `warnings`, `missing_fields`, `error`; report `page.truncated`, `data.budget.truncated`, `truncation_reasons`, `boundary`, writing "not returned" when absent; never read a full Graph or full Readable; never call `get_asset_detail`, `get_asset_summary`, `search_export_text`, or `request_targeted_snapshot`; list the actual call order at the end.

**Test 1 — Outline and stable sections.** Run `search_assets` → `get_asset_outline` → `get_readable_sections` → `get_readable_section` on two small sections. Pass when full `graph_id` values, node and edge counts, stable `section_id` values and character counts are reported, `returned` equals `total` for each section read, and the largest section is left unread.

**Test 2 — Locate and minimal subgraph.** Run `locate_graph_target`, then `get_graph_subgraph` with `direction=upstream`, `max_hops=2`, `max_nodes=40`, `max_characters=20000`. Pass when `ambiguous` results list all candidates and stop instead of self-selecting, a stable `node_id` is returned once unique, the subgraph is far smaller than the full graph with `budget.truncated=false`, and the answer states explicitly that this is not a full graph closure.

**Test 3 — Not-found and budget boundary.** Query a target that certainly does not exist, e.g. `__RAE_NOT_FOUND_TEST_9F3A__`; then re-run the subgraph with `max_nodes=1`. Pass when the first returns `resolution=not_found` without calling the subgraph tool and without reinterpreting the miss as a missing graph or asset, and the second returns `budget.truncated=true` with a specific `truncation_reasons`, a precise `boundary`, and an explicit statement that omitted nodes are not proven absent.

**Reference baseline** for hero asset `FX_Syst_Waterfall_FXTex`:

```text
Outline    4 graphs (7/5, 48/49, 25/35, 8/9), 7 stable sections
Subgraph   upstream 2 hops → 6 nodes / 5 links / 6,016 chars, not truncated
Truncated  max_nodes=1 → 1 node / 0 links / 1,954 chars
           truncation_reasons=[max_nodes], omitted_node_count=5
```

Full data is in `docs/V4.8_MVP_ACCEPTANCE_REPORT.md`.

## 7. Troubleshooting

**New tools missing, or still 7 tools.** Work through section 2 in order: marketplace registry first, then the actual Python process command line, then workspace config. Restart the client fully and start a new session afterwards.

**Editing the workspace `.mcp.json` changes nothing.** It is not the launch source. Check the marketplace registry.

**Killed processes respawn from the old path.** The client is relaunching the plugin from the registry. Fix the registry rather than killing processes repeatedly.

**Context Pack not found.** Set `READALL_EXPORT_ROOT` to `<YourProject>\Saved\ReadAllandExplainsExports`; remember `setx` needs a restart.

**MCP will not start.** Confirm `python --version` is 3.9+, then `/reload-plugins`. No npm and no third-party Python package is needed.

**`GRAPH_INDEX_DERIVED` or `READABLE_INDEX_DERIVED`.** Not an error. Indexes were derived deterministically from an existing 4.7 Pack. Do not present derived indexes as native UE fields.

**`GRAPH_IDENTITY_DEGRADED` or `GRAPH_DATA_INVALID`.** The former means legacy graph identity is incomplete but Outline and locate still work; the latter means duplicate node IDs prevent safe precise traversal. Both are deliberate explicit degradations, not silent failures.

**SyncLive request stuck at `pending`.** The UE editor must be running with the plugin loaded, outside PIE, and SyncLive Lite enabled in Editor Preferences.

## 8. Rollback

Reverse the changes in order; every step has a backup. Restore `known_marketplaces.json` from the `.bak` copy, remove `READALL_EXPORT_ROOT` if it did not exist before, terminate the current MCP process, then restart the client fully and run `/reload-plugins`.

For code, create a recovery branch from a backup tag rather than rewriting history:

```powershell
git tag -l "backup/v4.8-mvp-*"
git switch -c recover/from-cp4 backup/v4.8-mvp-cp4-20260809-<sha>
```

Constraints remain: no `reset --hard`, no force push, no moving released tags, and no overwriting uncommitted work in other worktrees.
