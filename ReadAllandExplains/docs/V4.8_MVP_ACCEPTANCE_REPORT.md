# ReadAllandExplains 4.8 Evidence MVP 双客户端验收报告

> 验收日期：2026-08-09
> 目标版本：`v4.8.0-preview.1`
> 开发分支：`feature/v4.8-evidence-mvp`
> 结论：**通过**。两个互不相关的客户端在同一不可变 Context Pack 上返回逐字段一致的证据。
> 文档职责：记录本轮人工验收的执行方式、真实返回数据、一致性比对结论与未验边界。真实 MCP 返回优先于本文。

## 1. 验收目标

本轮验收不是回归测试，而是回答一个产品问题：

> 4.8 的“定位目标 → 取最小证据 → 保留回链 → 诚实报告边界”是否真的成立，并且在不同客户端上可复现。

因此验收采用**双客户端独立执行**：Trans（WorkBuddy 侧）与 CodeBuddy 各自新建会话，使用同一份基准 Pack 和同一套问题，互不参考对方结果，最后逐字段比对。

## 3. 接入前置故障与根因

本轮验收开始前，两次出现“新接口不存在”。它不是功能缺陷，而是接入链路问题，记录在此以避免重复踩坑。

| 排查轮次 | 假设的启动源 | 实际结论 |
|---|---|---|
| 第一轮 | 工作区 `.mcp.json` | 已指向 4.8，但不是实际启动源 |
| 第一轮 | `config/mcporter.json` | 仍硬编码旧版本路径，修复后旧进程仍被拉起 |
| 第二轮 | CodeBuddy 插件市场注册表 | **真正根因**。`known_marketplaces.json` 中的 `readallandexplains-marketplace` 仍指向旧目录，插件自带 `.mcp.json` 用 `${CODEBUDDY_PLUGIN_ROOT}` 启动 MCP，因此进程始终来自旧代码 |

结论：**接入检查必须从实际启动源查起，而不是从看起来最相关的配置文件查起。**

正确排查顺序见 `docs/V4.8_ENVIRONMENT_SETUP.md`。

一个重要的正向信号：在接口缺失时，两个客户端都**主动停止并报告缺失**，没有回退到 `get_asset_summary` 等旧接口伪造结果。禁止静默降级的行为约束是有效的。

## 4. 验收方式

每轮测试都带以下硬约束，以保证结果是本轮真实返回，而不是模型复述历史答案：

- 数据必须来自本轮实际 MCP 返回，禁止引用历史结果、已知 ID 或预期值。
- 必须核对每次调用的 `pack_id`、`state`、`fingerprint`；不一致立即停止。
- 必须报告 `evidence`、`warnings`、`missing_fields`、`error`。
- 必须报告 `page.truncated`、`data.budget.truncated`、`truncation_reasons`、`boundary`；字段未返回时必须明确写“未返回”，不得留空或猜测。
- 禁止读取完整 Graph、完整 Readable。
- 禁止调用 `get_asset_detail`、`get_asset_summary`、`search_export_text`、`request_targeted_snapshot`。
- 必须在结尾列出本轮实际调用顺序。

### 顺带发现的资产问题

候选集暴露出命名不一致：三个纹理输入中，`FXTex2`、`FXTex3` 的前缀是 `SampleFXTex`，而 `FXTex1` 的前缀是 `SampleFXTex1`。

这是静态证据能发现、肉眼浏览大图时容易忽略的问题。需要注意边界：证据只能确认**Pin 标题存在差异**；是否为历史遗留、是否影响实际行为，需要在 UE 中确认，不能仅凭快照断言。

## 7. 测试三：异常路径与预算边界

### 测试 A：`not_found`

查询不存在的目标 `__RAE_NOT_FOUND_TEST_9F3A__`，两端均返回 `resolution=not_found`、`candidates=[]`、`evidence` 为空。

## 9. 双客户端一致性比对

这是本轮最有价值的结论。Trans 与 CodeBuddy 在互不参考的前提下，返回结果逐字段一致：

| 比对项 | 一致 |
|---|---|
| Pack `state` 与 `fingerprint` | 是 |
| 4 张 Graph 的完整 `graph_id`、节点数、连线数 | 是 |
| 7 个稳定 `section_id` 与字符量 | 是 |
| 章节行范围与字符范围 | 是 |
| 定位候选集（4 项）与 `match_type` 分布 | 是 |
| 唯一 `node_id` `558849D5-…-689167C8ADA9` | 是 |
| 子图规模 6 节点 / 5 连线 / 6016 字符 | 是 |
| Pin 级数据流与全部 `pin_id` | 是 |
| 截断态 1 节点 / 0 连线 / 1954 字符 | 是 |
| `truncation_reasons=[max_nodes]` | 是 |
| 边界连线 `/graphs/1/links/45` | 是 |
| `omitted_node_count=5` | 是 |

Trans 端额外返回了连线级 `json_pointer`（`/graphs/1/links/4、6、10、25、45`），其中 `links/45` 正是截断测试给出的边界连线，与子图最后一跳吻合。

由此得出的核心论据：

> 两个互不相关的客户端，在同一不可变 Pack 上，得到了逐字段相同的稳定 ID、子图规模、字符量和边界诊断。这说明 4.8 返回的是**可复现的确定性事实**，而不是模型每次即兴生成的近似解释。

这也是“证据标准”与“接一个大模型”的根本区别：确定性可以被第三方复核，解释不能。

## 9.1 SyncLive 定向补拍闭环（2026-08-09 晚补验）

补拍是本项目唯一会产生真实副作用的能力，因此按“预检 → 复述计划 → 等许可 → 才执行”的顺序验证。

预检阶段行为正确：完整报告参数约束（`asset_paths` 限 1–5 且必须 `/Game/` 开头、`permission_granted` 必须为 `true`、`dependency_depth` 限 0–1），复述计划后**停止等待许可**，未擅自提交；对“SyncLive 当前是否可受理”明确回答**未能确认**，并说明缺少独立健康检查接口，未拿 `list_context_packs` 冒充服务状态证明。

第一次提交（`rae-cp4-synclive-20260809-01`）失败，原因是指令未传 `pack_path`，服务自行选择了另一个 complete Pack（`ContextPack_20260807_103920_5ba69de66232_CE5302E4`，与基准 Pack 仅相差约 11 分钟），指纹校验必然不通过：

    "pack_id": "ContextPack_20260807_103920_5ba69de66232_CE5302E4",

## 9.2 冷启动缺口与材质链路（2026-08-09 晚）

材质冒烟连续两次停在起点，暴露出一个结构性缺口，其重要性高于材质兼容性本身。

**缺口**：必须先知道节点名才能使用 4.8，而节点名无法在不读整图的前提下获得。接口盘点确认三条路径全部堵死——`locate_graph_target` 的 `query` 必填且 `minLength=1`，`target_kind` 仅 `any`/`node`/`pin` 不接受类名；`get_asset_outline` 的 Graph 条目只有统计与身份字段，`entryPoints` 与 `searchIndex` 在派生实现中并未生成；`get_graph_subgraph` 的 `target_id` 必填。唯一出路是读整图，恰好违背 4.8 的立项前提。

Niagara 之所以顺利，是因为 `SampleFXTex` 这个名称恰好已知。两次停止本身是正确行为：第一次 `not_found` 后未换资产重试掩盖问题；第二次读到 `graph-ir` 只有统计后，明确区分“本轮章节未暴露节点清单”与“材质图没有节点”，未把看不到说成不存在。

**修复**（三项，均只改 MCP 侧，不动 C++ 与导出结构）：`locate_graph_target` 的 `query` 改为可选，省略时按图 IR 原始顺序枚举目标，返回 `resolution=listed`、`list_mode=true`、`match_type=listed`，并新增 `kind_filter` 支持按 `className` 或 `kind` 精确筛选；`not_found` 返回最多 10 条 `available_samples` 与 `discovery_hint`，附 `TARGET_NOT_FOUND_SAMPLES_PROVIDED` 警告，同时保留“a miss does not prove the node, Graph or asset is absent”的表述边界；`request_targeted_snapshot` 的 `pack_path` 改为必填，取消隐式基线选择，`BASE_PACK_FINGERPRINT_MISMATCH` 附 `available_complete_packs` 与操作提示。

**材质复验结果**（`M_FX_Waterfall_LargeDrips`，10 节点 / 10 连线）：

| 步骤 | 结果 |
|---|---|
| 枚举模式 | `resolution=listed`、`total=10`、无截断，`json_pointer` 由 `/graphs/0/nodes/0` 至 `/nodes/9` 严格递增 |
| 二次定位 | `MaterialExpressionMultiply_0` → `unique`，`match_type=exact_text`、`matched_field=name` |
| 上游子图 | `hops=2`、`nodes=4`、`links=3`、`characters=5241`、`omitted_node_count=2` |
| 截断诊断 | `budget.truncated=true`、`truncation_reasons=[max_hops]`，边界连线 `/graphs/0/links/0` 与 `/links/5` |
| `not_found` 引导 | 返回 10 条样例、`discovery_hint` 与 `TARGET_NOT_FOUND_SAMPLES_PROVIDED` |
| 降级警告 | 未出现 `GRAPH_IDENTITY_DEGRADED` 或 `GRAPH_DATA_INVALID` |

一个非设计预期的收获：`max_hops=2` 恰好卡在该材质图深度上，因此意外验证了 `max_nodes` 之外的**第二种截断原因**也能精确归因。边界指向 ScalarParameter `Opacity` 与 ParticleSubUV 到 `Multiply_1` 的两条输入，即诚实表达“该节点确有上游，但跳数预算不足，边界在此”，而非假装图到此结束。

跨类型一致性由此成立：

```text
Niagara Emitter Graph  48 节点  已知名称直接定位 → 6 节点子图  截断原因 max_nodes
Material Graph         10 节点  未知名称先枚举   → 4 节点子图  截断原因 max_hops
```

两种资产类型、两种发现路径、两种截断原因，Evidence 与 `json_pointer` 回链格式完全一致。

门禁：契约测试由 48 项扩展至 51 项全部通过（新增列举模式与顺序、`not_found` 样例与警告、工具层 `pack_path` 必填三项），Golden 22 项通过，`py_compile` 与 `git diff --check` 通过。

需要记录的一处隐蔽风险：原有快照测试直接调用 `submit_synclive_request` 方法层，绕过工具层 schema 校验，因此 `pack_path` 改为必填后旧测试不会失败。新增测试改走 `call_tool` 才真正锁住该契约。**测试未覆盖到的契约变更是静默回归的常见来源。**

## 3. Onboarding failure and root cause

Before acceptance could start, the new tools reported as missing twice. This was an onboarding issue, not a functional defect.

| Attempt | Assumed launch source | Actual finding |
|---|---|---|
| 1 | Workspace `.mcp.json` | Already pointed at 4.8, but was not the real launch source |

One positive signal: while the tools were missing, both clients **stopped and reported the gap** instead of silently falling back to legacy tools such as `get_asset_summary`. The no-silent-fallback constraint works.

## 4. Method

Every round enforced these constraints so answers could not be recited from history:

- Report `page.truncated`, `data.budget.truncated`, `truncation_reasons`, `boundary`; write "not returned" explicitly when absent.

- Never call `get_asset_detail`, `get_asset_summary`, `search_export_text`, `request_targeted_snapshot`.

## 9.1 SyncLive targeted re-snapshot loop (verified 2026-08-09)

Re-snapshot is the only capability in this project with real side effects, so it was verified in the order precheck → restate the plan → wait for permission → execute.

The precheck behaved correctly. It reported the full constraints (`asset_paths` limited to 1–5 canonical `/Game/` paths, `permission_granted` must be `true`, `dependency_depth` limited to 0–1), restated the plan and then **stopped to wait for permission** rather than submitting. ## 9.2 Cold-start gap and material path (2026-08-09)

Material smoke testing stopped at the very first step twice, exposing a structural gap more important than material compatibility itself.

**The gap.** You must already know a node name to use 4.8, yet node names cannot be obtained without reading the whole graph. An interface audit confirmed all three routes were closed: `locate_graph_target` required `query` with `minLength=1` and `target_kind` accepted only `any`/`node`/`pin` rather than class names; `get_asset_outline` exposed only per-graph counts and identity, with `entryPoints` and `searchIndex` never generated in the derived implementation; and `get_graph_subgraph` required `target_id`. The only remaining route was reading the full graph, which is exactly what 4.8 exists to avoid.

Niagara succeeded only because the name `SampleFXTex` happened to be known. Both stops were correct behaviour: after the first `not_found` the client did not swap assets to mask the problem, and after reading a statistics-only `graph-ir` section it explicitly distinguished "this section did not expose a node list" from "this material graph has no nodes".

**The fix** (three changes, all MCP-side, no C++ or export change). `query` became optional; omitting it enumerates targets in Graph IR order and returns `resolution=listed`, `list_mode=true` and `match_type=listed`, and a new `kind_filter` selects by exact `className` or `kind`. A `not_found` result now returns up to 10 `available_samples` plus a `discovery_hint` and a `TARGET_NOT_FOUND_SAMPLES_PROVIDED` warning, while still stating that a miss does not prove the node, Graph or asset is absent. `request_targeted_snapshot` now requires `pack_path`, removing implicit baseline selection, and `BASE_PACK_FINGERPRINT_MISMATCH` reports `available_complete_packs` with an actionable hint.

**Material re-verification** on `M_FX_Waterfall_LargeDrips` (10 nodes / 10 links): enumeration returned `resolution=listed` with `total=10`, untruncated, and `json_pointer` values strictly ascending from `/graphs/0/nodes/0` to `/nodes/9`; re-location of `MaterialExpressionMultiply_0` returned `unique` via `exact_text` on `matched_field=name`; the upstream slice returned `hops=2`, `nodes=4`, `links=3`, `characters=5241`, `omitted_node_count=2`, with `budget.truncated=true`, `truncation_reasons=[max_hops]` and boundary edges `/graphs/0/links/0` and `/links/5`; the `not_found` probe returned 10 samples with the hint and warning; and neither `GRAPH_IDENTITY_DEGRADED` nor `GRAPH_DATA_INVALID` appeared.

An unplanned benefit: `max_hops=2` happened to sit exactly at this graph's depth, so a **second truncation reason** beyond `max_nodes` was attributed precisely. The boundary points at the ScalarParameter `Opacity` and ParticleSubUV inputs feeding `Multiply_1`, honestly stating "this node does have upstream, but the hop budget stopped here" instead of implying the graph ends there.

Cross-type consistency therefore holds:

```text
Niagara emitter graph  48 nodes  known name, direct locate → 6-node slice  reason max_nodes
Material graph         10 nodes  unknown name, enumerate   → 4-node slice  reason max_hops
```

Two asset types, two discovery paths, two truncation reasons, and identical evidence and `json_pointer` back-link formats.

Gates: contract tests grew from 48 to 51 and all pass (enumeration order, `not_found` samples and warning, tool-level mandatory `pack_path`), Golden 22 tests pass, and `py_compile` and `git diff --check` pass.

One subtle risk worth recording: existing snapshot tests call `submit_synclive_request` at the method level, bypassing tool-level schema validation, so making `pack_path` mandatory did not fail them. The new test goes through `call_tool` and therefore actually locks the contract. **Contract changes not covered by tests are a common source of silent regression.**
