# ReadAllandExplains 4.8 Evidence MVP 双客户端验收报告

> 验收日期：2026-08-09
> 目标版本：`v4.8.0-preview.1`
> 开发分支：`feature/v4.8-evidence-mvp`
> 结论：**通过**。两个互不相关的客户端在同一不可变 Context Pack 上返回逐字段一致的证据。
> 文档职责：记录本轮人工验收的执行方式、真实返回数据、一致性比对结论与未验边界。真实 MCP 返回优先于本文。

## 1. 验收目标

本轮验收不是回归测试，而是回答一个产品问题：

> 4.8 的“定位目标 → 取最小证据 → 保留回链 → 诚实报告边界”是否真的成立，并且在不同客户端上可复现。

因此验收采用**双客户端独立执行**：Trans（WorkBuddy 侧）与 CodeBuddy 各自新建会话，使用同一份基准 Pack 和同一套问题，互不参考对方结果，最后逐字段比对。

## 3. 接入前置故障与根因

本轮验收开始前，两次出现“新接口不存在”。它不是功能缺陷，而是接入链路问题，记录在此以避免重复踩坑。

| 排查轮次 | 假设的启动源 | 实际结论 |
|---|---|---|
| 第一轮 | 工作区 `.mcp.json` | 已指向 4.8，但不是实际启动源 |
| 第一轮 | `config/mcporter.json` | 仍硬编码旧版本路径，修复后旧进程仍被拉起 |
| 第二轮 | CodeBuddy 插件市场注册表 | **真正根因**。`known_marketplaces.json` 中的 `readallandexplains-marketplace` 仍指向旧目录，插件自带 `.mcp.json` 用 `${CODEBUDDY_PLUGIN_ROOT}` 启动 MCP，因此进程始终来自旧代码 |

结论：**接入检查必须从实际启动源查起，而不是从看起来最相关的配置文件查起。**

正确排查顺序见 `docs/V4.8_ENVIRONMENT_SETUP.md`。

一个重要的正向信号：在接口缺失时，两个客户端都**主动停止并报告缺失**，没有回退到 `get_asset_summary` 等旧接口伪造结果。禁止静默降级的行为约束是有效的。

## 4. 验收方式

每轮测试都带以下硬约束，以保证结果是本轮真实返回，而不是模型复述历史答案：

- 数据必须来自本轮实际 MCP 返回，禁止引用历史结果、已知 ID 或预期值。
- 必须核对每次调用的 `pack_id`、`state`、`fingerprint`；不一致立即停止。
- 必须报告 `evidence`、`warnings`、`missing_fields`、`error`。
- 必须报告 `page.truncated`、`data.budget.truncated`、`truncation_reasons`、`boundary`；字段未返回时必须明确写“未返回”，不得留空或猜测。
- 禁止读取完整 Graph、完整 Readable。
- 禁止调用 `get_asset_detail`、`get_asset_summary`、`search_export_text`、`request_targeted_snapshot`。
- 必须在结尾列出本轮实际调用顺序。

### 定位过程

以 `SampleFXTex` 查询 `Waterfall_0` Graph，两端均返回 `resolution=ambiguous`，候选 4 项：

| `node_id` | `name` | `title` | `kind` | `match_type` |
|---|---|---|---|---|
| `558849D5-4DE8-EDC8-BA5E-689167C8ADA9` | `NiagaraNodeFunctionCall_3` | `SampleFXTex` | `NiagaraNodeFunctionCall` | `exact_text` |
| `30797B05-4FB7-5538-3356-1AB890C00FE2` | `NiagaraNodeInput_10` | `SampleFXTex.FXTex3` | `NiagaraNodeInput` | `prefix` |
| `4F57766F-4224-6352-BAC2-E89886693E0B` | `NiagaraNodeInput_0` | `SampleFXTex.FXTex2` | `NiagaraNodeInput` | `prefix` |
| `8A6B0CD1-4471-3B19-A411-A597980FCBC4` | `NiagaraNodeInput_8` | `SampleFXTex1.FXTex1` | `NiagaraNodeInput` | `prefix` |

按显式规则（`title` 精确等于 `SampleFXTex` 且 `kind` 为 `NiagaraNodeFunctionCall`）二次定位，得到 `resolution=unique`，`node_id=558849D5-4DE8-EDC8-BA5E-689167C8ADA9`。

关键行为：`ambiguous` 时**列出候选并停下**，未自动选择“看起来最像”的那个。歧义消解由显式规则完成，不是模型偏好。

### 最小上游子图

请求参数：`direction=upstream`、`max_hops=2`、`max_nodes=40`、`max_characters=20000`。

实际返回：`hops=2`、`nodes=6`、`characters=6016`、`omitted_node_count=0`、`omitted_boundary_count=0`、`budget.truncated=false`、`truncation_reasons=[]`、`boundary=[]`。

还原出的 Pin 级数据流：

```text
NiagaraNodeInput_8  (SampleFXTex1.FXTex1) → Map Set.SampleFXTex.FXTex1
NiagaraNodeInput_0  (SampleFXTex.FXTex2)  → Map Set.SampleFXTex.FXTex2
NiagaraNodeInput_10 (SampleFXTex.FXTex3)  → Map Set.SampleFXTex.FXTex3
NiagaraNodeInput_4  (InputMap)            → Map Set.Source
Map Set.Dest                              → SampleFXTex.InputMap
```

目标节点还返回了跨图跳转所需的 `reference_path` 与 `callee_graph_id`，指向被调用的 `SampleFXTex` Module Graph，为后续跨图追踪提供稳定入口。

两端均明确判定：**这不是完整 Graph 闭包**，依据是方向为上游、跳数上限为 2、6/48 节点、5/49 连线，且 `budget.truncated=false` 只说明本次请求范围内未截断，不代表整图已读完。

判定：**通过。** 这是本轮最关键的一题，Before/After 差异见第 8 节。

### 顺带发现的资产问题

候选集暴露出命名不一致：三个纹理输入中，`FXTex2`、`FXTex3` 的前缀是 `SampleFXTex`，而 `FXTex1` 的前缀是 `SampleFXTex1`。

这是静态证据能发现、肉眼浏览大图时容易忽略的问题。需要注意边界：证据只能确认**Pin 标题存在差异**；是否为历史遗留、是否影响实际行为，需要在 UE 中确认，不能仅凭快照断言。

## 7. 测试三：异常路径与预算边界

### 测试 A：`not_found`

查询不存在的目标 `__RAE_NOT_FOUND_TEST_9F3A__`，两端均返回 `resolution=not_found`、`candidates=[]`、`evidence` 为空。

正确行为：未继续对该目标调用 `get_graph_subgraph`；未把“未找到该目标”解释为“该 Graph 不存在”或“该资产不存在”。

### 测试 B：预算截断

请求参数：`direction=upstream`、`max_hops=8`、`max_nodes=1`、`max_characters=20000`。

实际返回：`nodes=1`、`links=0`、`hops=0`、`characters=1954`、`omitted_node_count=5`、`omitted_boundary_count=0`、`budget.truncated=true`、`truncation_reasons=[max_nodes]`，并附加 `BUDGET_TRUNCATED` 警告。

边界连线完整返回：

```json
{
  "from_node_id": "EF2C500C-405F-0E51-1505-5286B40AB3E3",
  "from_pin_id": "4EED079A-4D60-DAB6-FFC5-0E9430ECC4CB",
  "to_node_id": "558849D5-4DE8-EDC8-BA5E-689167C8ADA9",
  "to_pin_id": "4BB49B03-4C4A-3192-BC1D-E9BA5038FC0B",
  "reason": "max_nodes",
  "json_pointer": "/graphs/1/links/45"
}
```

三处自洽性验证：

1. 截断原因与设定的 `max_nodes=1` 严格对应，不是笼统的“结果过大”。
2. `omitted_node_count=5` 与测试二的 6 节点相减吻合（保留目标节点 1 个，省略 5 个）。
3. 边界连线 `/graphs/1/links/45` 正是测试二完整子图的最后一跳（`Map Set.Dest → SampleFXTex.InputMap`）。

判定：**通过。** 预算不足时目标节点仍被保留，边界被精确指出，且明确声明不得把未返回节点解释为不存在。

## 8. 答辩用 Before / After

```text
Before  4.7：整图读取
        48 节点 / 49 连线 / 约 101,734 字符 → 超过 60,000 上限，返回 RESULT_TOO_LARGE

After   4.8：定位后取最小证据

边界    max_nodes=1 强制截断
```

字符口径说明，避免答辩现场被追问时出现前后矛盾：`6,016` 是子图数据本身的字符量；`13,757` 是包含完整响应信封（Envelope、Evidence、诊断字段）的字符量。两者都在预算内，指代范围不同，不可混用。

## 9. 双客户端一致性比对

这是本轮最有价值的结论。Trans 与 CodeBuddy 在互不参考的前提下，返回结果逐字段一致：

| 比对项 | 一致 |
|---|---|
| Pack `state` 与 `fingerprint` | 是 |
| 4 张 Graph 的完整 `graph_id`、节点数、连线数 | 是 |
| 7 个稳定 `section_id` 与字符量 | 是 |
| 章节行范围与字符范围 | 是 |
| 定位候选集（4 项）与 `match_type` 分布 | 是 |
| 唯一 `node_id` `558849D5-…-689167C8ADA9` | 是 |
| 子图规模 6 节点 / 5 连线 / 6016 字符 | 是 |
| Pin 级数据流与全部 `pin_id` | 是 |
| 截断态 1 节点 / 0 连线 / 1954 字符 | 是 |
| `truncation_reasons=[max_nodes]` | 是 |
| 边界连线 `/graphs/1/links/45` | 是 |
| `omitted_node_count=5` | 是 |

Trans 端额外返回了连线级 `json_pointer`（`/graphs/1/links/4、6、10、25、45`），其中 `links/45` 正是截断测试给出的边界连线，与子图最后一跳吻合。

由此得出的核心论据：

> 两个互不相关的客户端，在同一不可变 Pack 上，得到了逐字段相同的稳定 ID、子图规模、字符量和边界诊断。这说明 4.8 返回的是**可复现的确定性事实**，而不是模型每次即兴生成的近似解释。

这也是“证据标准”与“接一个大模型”的根本区别：确定性可以被第三方复核，解释不能。

## 10. 未验边界

本报告不覆盖以下内容，不得据此声称已验证：

- `request_targeted_snapshot` 权限门禁与 SyncLive 补拍闭环：需要 UE 编辑器运行、插件已加载、不处于 PIE 且 SyncLive Lite 开启。
- 插件原生 `graphIndex` 与章节元数据（CP3）：本轮索引为 MCP 内存派生，C++ 与导出结构未修改，因此未声称完成 UE 5.7 编译。
- 材质与材质函数的最小子图链路：本轮英雄链路只覆盖 Niagara Emitter Graph。
- 运行时事实：静态快照无法证明 PIE 时序、逐帧 GPU 结果、动态 Render Target 内容与参数最终值。
- 旧 Pack 的已知兼容边界：Node ID 重复的旧材质在精确遍历时以 `GRAPH_DATA_INVALID` 停止；Pin 的稳定身份必须联合 `nodeId + pinId`。

# 4.8 Evidence MVP Dual-Client Acceptance Report (English)

> Date: 2026-08-09
> Target version: `v4.8.0-preview.1`
> Branch: `feature/v4.8-evidence-mvp`
> Verdict: **PASS**. Two unrelated clients returned field-for-field identical evidence from the same immutable Context Pack.

## 1. Goal

This round was not a regression run. It answered one product question:

> Does "locate the target, read the minimum evidence, keep the back-links, report the boundary honestly" actually hold, and is it reproducible across clients?

Two clients (Trans and CodeBuddy) ran the same question set independently against the same baseline Pack, without seeing each other's output. Results were then compared field by field.

## 2. Environment

| Item | Value |
|---|---|
| MCP server version | `0.6.0` |
| Tool count | `12` |
| New 4.8 tools | `get_asset_outline`, `locate_graph_target`, `get_graph_subgraph`, `get_readable_sections`, `get_readable_section` |
| UE plugin version | `4.7.0` (no C++ or export change this round) |
| Baseline Pack | `ContextPack_20260807_102814_771605c4d7cc_6151D702` |
| Pack state | `complete` |
| Pack fingerprint | `sha1:cfe3cc9a8250552c87fb5a1779fb1c4f88a04209` |
| Hero asset | `/Game/TALibrary/CommonTools/Envirment/WaterfallTool/Particles/FX_Syst_Waterfall_FXTex.FX_Syst_Waterfall_FXTex` |

All query capabilities are derived deterministically in MCP memory from existing 4.7 Raw Facts. No asset was re-exported, no Pack was rewritten, and neither Manifest nor Pack fingerprint was affected. Legacy Packs therefore return `GRAPH_INDEX_DERIVED` and `READABLE_INDEX_DERIVED`, which are expected provenance hints and must not be presented as native UE fields.

## 3. Onboarding failure and root cause

Before acceptance could start, the new tools reported as missing twice. This was an onboarding issue, not a functional defect.

| Attempt | Assumed launch source | Actual finding |
|---|---|---|
| 1 | Workspace `.mcp.json` | Already pointed at 4.8, but was not the real launch source |
| 1 | `config/mcporter.json` | Still hardcoded the old path; after fixing it, old processes still respawned |
| 2 | CodeBuddy marketplace registry | **True root cause.** `readallandexplains-marketplace` in `known_marketplaces.json` still pointed at the old directory; the plugin's own `.mcp.json` launches MCP via `${CODEBUDDY_PLUGIN_ROOT}`, so the process always came from old code |

Lesson: **start from the actual launch source, not from the config file that looks most relevant.** See `docs/V4.8_ENVIRONMENT_SETUP.md`.

One positive signal: while the tools were missing, both clients **stopped and reported the gap** instead of silently falling back to legacy tools such as `get_asset_summary`. The no-silent-fallback constraint works.

## 4. Method

Every round enforced these constraints so answers could not be recited from history:

- All data must come from this round's actual MCP responses; no historical results, known IDs, or expected values.
- Verify `pack_id`, `state`, and `fingerprint` on every call; stop immediately on mismatch.
- Report `evidence`, `warnings`, `missing_fields`, `error`.
- Report `page.truncated`, `data.budget.truncated`, `truncation_reasons`, `boundary`; write "not returned" explicitly when absent.
- Never read a full Graph or full Readable document.
- Never call `get_asset_detail`, `get_asset_summary`, `search_export_text`, `request_targeted_snapshot`.
- List the actual call order at the end.

## 5. Test 1: Outline and stable sections

Order: `search_assets` → `get_asset_outline` → `get_readable_sections` → `get_readable_section` × 2.

Four graphs were reported with full `graph_id` values, no ellipsis: `SystemScriptGraph` (7/5), the `Waterfall_0` emitter graph (48/49), and two project module graphs (25/35 and 8/9).

Seven stable sections were returned: `overview` (356), `parameters` (252), `relationships` (4284), `graph-ir` (412), `niagara-details` (1050), `technical` (88601), `ai-prompt` (338). The original Markdown has 34 H2 headings, collapsed into 7 stable outer sections. The 88,601-character `technical` section appeared in the index only; neither client read its body, and neither loaded the ~96 KB document. That is exactly the point of a stable section index: **know what exists and how large it is before deciding what to read.**

Precise reads: `parameters` returned 252/252 (lines 16–27, chars 455–707); `niagara-details` returned 1050/1050 (lines 123–144, chars 5403–6453). Neither was truncated.

Facts obtained: three Texture-typed User parameters (`User.FXTex1/2/3`); one sprite renderer bound to `M_FX_Waterfall_LargeDrips` with 27 bindings; three fingerprint-deduplicated curves (2, 2, and 3 keys, each retaining 4 `usedBy` sources).

Verdict: **PASS.** Sections were read by stable `section_id`, never by guessed line numbers, and evidence carried both line and Unicode character ranges.

## 6. Test 2: Locate and minimal subgraph

Querying `SampleFXTex` returned `resolution=ambiguous` with four candidates: one `NiagaraNodeFunctionCall` matched by `exact_text`, and three `NiagaraNodeInput` nodes matched by `prefix`. Both clients **listed the candidates and stopped** instead of picking the most plausible one. Disambiguation was then performed by an explicit rule (`title` equals `SampleFXTex` and `kind` is `NiagaraNodeFunctionCall`), yielding `resolution=unique` with `node_id=558849D5-4DE8-EDC8-BA5E-689167C8ADA9`.

Subgraph request `direction=upstream`, `max_hops=2`, `max_nodes=40`, `max_characters=20000` returned `hops=2`, `nodes=6`, `characters=6016`, `omitted_node_count=0`, `budget.truncated=false`, `boundary=[]`.

Reconstructed pin-level data flow:

```text
NiagaraNodeInput_8  (SampleFXTex1.FXTex1) → Map Set.SampleFXTex.FXTex1
NiagaraNodeInput_0  (SampleFXTex.FXTex2)  → Map Set.SampleFXTex.FXTex2
NiagaraNodeInput_10 (SampleFXTex.FXTex3)  → Map Set.SampleFXTex.FXTex3
NiagaraNodeInput_4  (InputMap)            → Map Set.Source
Map Set.Dest                              → SampleFXTex.InputMap
```

The target node also returned `reference_path` and `callee_graph_id` pointing at the callee module graph, providing a stable entry point for cross-graph tracing.
